## useAgUiRuntime 选项

| 选项 | 类型 | 描述 |
| --- | --- | --- |
| `agent` | `HttpAgent` | AG-UI 客户端代理（来自 `@ag-ui/client`）。必填。 |
| `logger` | `Partial<Logger>` | 可选的日志记录器覆盖配置。运行时会记录事件解析器警告和运行生命周期事件。 |
| `showThinking` | `boolean` | 是否将 `THINKING_*` 和 `REASONING_*` 事件渲染为可见的推理内容。默认为 `true`。 |
| `autoCancelPendingToolCalls` | `boolean` | 当用户发送、编辑或重新加载消息时，是否自动取消未解决的客户端工具调用。默认为 `true`。参见[下文](#auto-cancelling-pending-tool-calls)。 |
| `onError` | `(e: Error) => void` | 在 `RUN_ERROR` 事件和协议错误发生时触发的错误回调。 |
| `onCancel` | `() => void` | 运行被取消时触发的取消回调，包括用户取消和运行时销毁。 |
| `adapters` | `UseAgUiRuntimeAdapters` | 标准适配器插槽（见下文）。 |

## 加载会话历史

如果后端公开了某个会话中持久化的 AG-UI 消息（例如 `GET /agents/state` 端点），请使用 `fromAgUiMessages` 将其转换为 assistant-ui 消息，并从历史记录适配器中返回这些消息，以便线程在页面加载时恢复：

```tsx
import { fromAgUiMessages } from "@assistant-ui/react-ag-ui";
import { ExportedMessageRepository } from "@assistant-ui/react";

const runtime = useAgUiRuntime({
  agent,
  adapters: {
    history: {
      async load() {
        const { messages } = await fetch("/agents/state").then((r) => r.json());
        return ExportedMessageRepository.fromArray(fromAgUiMessages(messages));
      },
      async append({ message }) {
        // persist the newly sent message on your backend
      },
    },
  },
});
```

会话期间发送的消息始终会通过运行输入转发给代理，与 `append` 无关。因此，只有当后端已经自行持久化会话时，空操作 `append` 才是安全的；否则，这些消息会在下一次页面加载时丢失。

`fromAgUiMessages` 接受一个可选的第二个参数：传入 `{ showThinking: false }`，以匹配配置了 `showThinking: false` 的运行时。这样，导入的推理消息中的可读文本会在转换时被丢弃，就像实时运行永远不会存储该文本一样。消息上的 `encryptedValue` 会被保留，因为它是不透明的状态，代理需要将其取回，而不是该选项要隐藏的内容。

推理会以其到达时的形状完成往返。`fromAgUiMessages` 会将 `reasoning` 记录导入为包含推理部分的助手消息，而运行输入会将该部分转换回独立的 `reasoning` 记录，而不是将其丢弃，因此重新加载的线程会在下一次运行时保留其推理历史。若助手消息中的推理部分同时包含文本或工具调用，则该推理部分会作为独立的 `reasoning` 记录，在该助手记录之前输出；AG-UI 消息体不携带运行标识，因此无法恢复推理在一次运行中的原始位置。

加密值也会随之保留。AG-UI 将其描述为不透明的思维链数据块，由客户端存储并转发以保持状态连续性，而不是根据文本计算出的签名。携带 `encryptedValue` 的导入 `ReasoningMessage` 会将其保留在部分的 `providerMetadata.agui.encryptedValue` 中，而实时运行会从 `REASONING_ENCRYPTED_VALUE` 事件中获取相同的值（`subtype: "message"`，键为 `entityId`）。因此，来自任一来源的推理都会以完整保留该值的形式重新输出，需要取回该值的代理也能够重放它。当一条记录的可读 `content` 为空，且其负载完全位于 `encryptedValue` 中时，这就是 AG-UI 在代理声明 `capabilities.reasoning.encrypted` 时描述的零数据保留形式，该记录仅在导入路径上保留。它按设计没有任何可渲染内容，因此不会成为消息或部分；它会附加到线路上与其相邻的消息的 `metadata.custom.agui.opaqueReasoning` 中，并在运行输入中重放到该消息旁边。`showThinking` 不会丢弃它。该选项会将推理从 UI 中隐藏，而加密值是不透明的状态，代理需要将其取回，并非用于渲染的内容，因此隐藏的记录会保留该值，只丢失可读文本。这是导入路径的保证：启用 `showThinking: false` 的实时运行不会打开推理块，因此运行期间到达的 `REASONING_ENCRYPTED_VALUE` 无法解析到任何槽位，也不会被保留。因此，同一线程在重新加载后会携带该值，但不会在产生它的实时会话中携带该值。直接调用 `fromAgUiMessages` 的使用者看到的是元数据，而不是部分。

该记录有三个限制。不会输出可读内容的实时流不会生成推理部分，因此运行时没有可供附加该值的对象；只有 `fromAgUiMessages` 会保留它，无论是由你直接调用，还是由运行时在导入 `MESSAGES_SNAPSHOT` 时为你调用。位于助手消息及其自身工具结果之间的记录，会在该工具结果之后重放，而不是位于二者之间，因为导入过程会将结果折叠到助手消息中，而导出时边界已经消失。快照中没有其他消息的记录没有可供锚定的对象，因此会被丢弃。

协议要求将推理发回，因此入站端必须处理它。出于这一原因，`ag-ui-langgraph` 值得固定版本：在 0.0.36 之前，任何产生过推理的线程在第二轮运行时都会抛出 `ValueError: Unsupported message role: reasoning`，因为其转换器只识别用户、助手、系统和工具角色。0.0.36 会跳过入站的 `reasoning` 和 `developer` 记录，而不是抛出错误，因此该轮运行能够成功，但推理会被丢弃。0.0.42 会将入站的 `reasoning` 记录重新附加为其后续助手消息上的内容块，其中也包括加密内容，因此重放内容确实能够到达模型；如果其后没有助手消息，该记录仍会在那里被丢弃，这正是在线程最后一条消息之后重放的记录的结果。请至少使用 0.0.36，以避免错误；如需让重放真正有意义，请至少使用 0.0.42。

服务器如何处理重放的记录仍由服务器自行决定，因此应将连续性视为尽力而为，而不是保证。`ag-ui-langgraph` 涵盖了这三个版本中的全部三种行为，其他集成可能采用其中任意一种；只有在服务器转发 `encryptedValue` 的情况下，它才会到达提供商。

`fromAgUiMessages` 会重建每条消息的文本、推理和工具调用。多模态用户输入（`image`、`audio`、`video` 和 `document` 部分，以及旧版 `binary` 部分）会作为用户消息上的附件恢复。因此，持久化多模态消息的后端会在重新加载时再次显示它们，并在下一次运行时重新发送它们。仅引用文件 ID 的旧版 `binary` 部分不会被恢复。

如果助手消息中的工具调用没有匹配的工具结果，则会以 `requires-action` 状态重建，这与运行时为待处理工具调用推导出的状态相同。因此，重新加载后的人在回路工具调用（例如 `ask_user` 工具）仍可操作，而不会陷入卡住状态。这与其他外部状态存储运行时在重新加载时呈现待处理工具调用的方式一致。AG-UI 线路快照不携带运行结果，因此，即使某次成功运行有意留下了没有结果的工具调用，该调用也会被呈现为可操作状态。

当后端将中断持久化到助手消息上时，中断也会被恢复。AG-UI 消息体没有中断字段，因此请将运行时自身的 `metadata.custom.agui.interrupts` 数组与消息一起持久化；`fromAgUiMessages` 会读取该数组，重建 `requires-action` / `interrupt` 状态，并重新附加元数据，因此 `getPendingInterrupts`、`useAgUiInterrupts` 和 `submitInterruptResponses` 在重新加载后仍可正常工作。如果同一消息上同时存在待处理工具调用和中断，则以中断状态为准。没有持久化的数组，就无法重建中断状态。

## 构建 AG-UI 运行输入

`toAgUiMessages` 是运行时用于构建 `runAgent` 输入的转换器。当你负责传输层（例如 AG-UI WebSocket），并且需要对 `onNew` 的 `AppendMessage` 进行相同的转换时，请使用它：

```tsx
import { toAgUiMessages } from "@assistant-ui/react-ag-ui";

const [agUiMessage] = toAgUiMessages([message]);
```

`AppendMessage` 没有 `id`。转换器会为其分配一个，以满足 AG-UI 消息架构的要求。调用方提供的 id 会被保留。每次调用都会生成新的 id，因此请转换一次后发送该对象。只有 `user`、`assistant`、`system`、`developer`、`tool` 和 `reasoning` 输入会被转换。

## 线程列表（实验性）

<Callout type="warn">
线程列表适配器目前处于实验阶段，可能会在不另行通知的情况下发生变化。
</Callout>

`UseAgUiThreadListAdapter` 允许你使用自己的状态管理线程列表。

| 选项 | 类型 | 描述 |
| --- | --- | --- |
| `threadId` | `string` | 当前处于活动状态的线程 ID。 |
| `onSwitchToNewThread` | `() => Promise<void>` | 用户创建新线程时调用。在此处重置线程状态。 |
| `onSwitchToThread` | `(threadId: string) => Promise<{ messages, state? }>` | 用户切换线程时调用。返回已持久化的消息（以及可选的不透明状态）。 |

```tsx
const runtime = useAgUiRuntime({
  agent,
  adapters: {
    threadList: {
      threadId: currentThreadId,
      onSwitchToNewThread: async () => {
        setCurrentThreadId(await createThread());
      },
      onSwitchToThread: async (id) => {
        const { messages, state } = await loadThread(id);
        setCurrentThreadId(id);
        return { messages, state };
      },
    },
  },
});
```

## 中断（实验性）

<Callout type="warn">
中断 API 具有实验性，可能会随时更改，恕不另行通知。
</Callout>

当代理发出 `RUN_FINISHED` 并携带 `outcome = { type: "interrupt", interrupts: [...] }` 时，活动助手消息会被标记为 `requires-action`，并附带 `reason: "interrupt"`；`Interrupt[]` 负载会写入 `metadata.custom.agui.interrupts`。接下来可以据此渲染审批 / 输入 UI。

由于协议只会在 `RUN_FINISHED` 上携带结果，因此运行仍处于打开状态时，已注册的前端工具不会运行：其 `execute` 会在运行结果已知后触发，所以网关不会落在客户端已经执行过的调用上。

`useAgUiRuntime` 返回一个 `AgUiAssistantRuntime`，并额外提供两个方法：

| 方法 | 描述 |
| --- | --- |
| `unstable_getPendingInterrupts(): readonly AgUiInterrupt[]` | 最近一条助手消息中处于打开状态的中断的快照。 |
| `unstable_submitInterruptResponses(responses: ResumeEntry[]): Promise<void>` | 为每个处于打开状态的中断提交一个 `ResumeEntry`，并恢复运行。 |

`responses` 必须处理每个处于打开状态的中断；缺少条目、未知 ID 或已过期的中断（`expiresAt`）会在发起任何网络调用前被拒绝。每个条目都是 `{ interruptId, status: "resolved" | "cancelled", payload? }`。下一条 `RunAgentInput` 会携带 `resume: ResumeEntry[]`。

```tsx
const runtime = useAgUiRuntime({ agent });
const pending = runtime.unstable_getPendingInterrupts();

await runtime.unstable_submitInterruptResponses(
  pending.map((i) => ({
    interruptId: i.id,
    status: "resolved",
    payload: { approved: true },
  })),
);
```

### 从中断转向其他操作

当用户忽略中断 UI，直接发送新消息时，请使用 `useAgUiSteerAway` hook。每个处于打开状态的中断默认会被设为 `status: "cancelled"`，新消息会被追加，并在传输层中携带 `resume: ResumeEntry[]` 以恢复运行。

同一个 hook 也可以从待处理的客户端工具调用转向其他操作。当头部助手消息处于 `requires-action` 状态，并带有 `reason: "tool-calls"`（等待结果的前端工具）时，如果用户发送新消息，所有未解决的工具调用都会被取消，并返回错误结果；消息会被完成，同时启动一次新的运行，并将这些取消操作纳入其历史记录。在此情况下传入 `responses` 会抛出异常，因为响应只能处理中断。没有待处理项时，`steerAway` 的行为与普通追加相同。

```tsx
const steerAway = useAgUiSteerAway();

// the user typed a new message instead of answering the interrupt
await steerAway("actually, let's do something else");
```

该消息接受普通字符串或部分 `AppendMessage`（父级默认使用当前头部，即被中断的助手消息）。传入 `responses` 可覆盖特定中断的状态；其余中断仍默认被取消。

```tsx
await steerAway("continue without the file", [
  { interruptId: "tool-1", status: "resolved", payload: { approved: true } },
]);
```

### 自动取消待处理的工具调用

默认情况下，运行时会自动完成工具调用的取消部分：当客户端工具调用仍未解决，而用户发送新消息、编辑较早的消息或重新加载页面时，所有未解决的工具调用都会收到相同的取消错误结果，助手消息会被完成，运行会继续，并将这些取消操作纳入其历史记录。设置 `autoCancelPendingToolCalls: false` 可选择退出此行为；此时，普通发送不会解决待处理的工具调用，而[从中断转向其他操作](#steering-away-from-an-interrupt)仍是取消它们的显式方式。

待处理的中断永远不会被自动取消：中断处于打开状态时发送消息仍会抛出异常，必须使用 `useAgUiSubmitInterruptResponses` 回答中断，或使用 `useAgUiSteerAway` 丢弃中断。

## 子代理

采用 agents-as-tools 模式运行代理的后端，会在每个子代理产生的事件中发出 `SUBAGENT_STARTED` / `SUBAGENT_FINISHED` / `SUBAGENT_ERROR`，并附带一个 `subagentRunId`。运行时会将这些活动归组为每次子代理运行对应的一条嵌套助手消息，并通过 `ToolCallMessagePart.messages` 将其附加到生成该子代理的工具调用上，再通过 `SUBAGENT_STARTED.parentToolCallId` 将二者关联。[`MessagePartPrimitive.Messages`](/docs/tools/multi-agent) 无需额外接线即可渲染这些内容，而本次运行的 `name`、`description`、`parentSubagentRunId`、`result`、`interruptIds` 和 `errorCode` 会通过嵌套消息的 `metadata.custom.agui` 传递。

没有命名任何可达生成调用的子代理没有可嵌套的位置，因此其输出会渲染在父线程中，而不会被丢弃。`parentToolCallId` 是可选的，可以命名本次运行从未见过的调用；两个运行也可以互相命名。在这些情况下，都会回退为扁平渲染，这与协议自身在子代理之前执行的兼容性中间件所进行的降级一致。格式错误或存在循环的父级链会受到深度保护限制，而不会被继续追踪。

对于运行已经见过的 id，重复出现的 `SUBAGENT_STARTED` 会被视为延续，因为挂起的子代理会在恢复时重新声明。它会刷新描述性字段并重新打开状态，但绝不会重新设置已建立运行的父级关系，否则已经渲染的输出会被移动到另一个工具调用下。

子代理在前端执行的工具调用与根代理的行为相同：嵌套在 `ToolCallMessagePart.messages` 上的调用可以通过 `getPendingToolCalls()` 访问，通过 `addToolResult` 解析，其结果会作为生成该调用的助手记录上的 `tool` 记录，随恢复操作传递。审批门也涵盖嵌套调用，因此，命名子代理作用域内调用的门会投影到嵌套部分；门处于打开状态时，前端工具不会执行；而未决门的结果永远不会导出到后端。

在依赖此功能之前，需要了解以下两个限制：

- **重新加载后嵌套结构不会保留。** 线程恢复会读取扁平化的线协议结构，因此恢复后的子代理工具调用会作为根级部分返回，而不会嵌套在生成它的调用下。结果和决策都会保留，只有嵌套关系不会保留。

- **嵌套的人在回路没有恢复路径。** 携带 `suspended` 结果的 `SUBAGENT_FINISHED` 会标记嵌套消息的 `requires-action`，并在消息元数据中保留其 `interruptIds`，但目前还没有任何机制响应这些内容。

### 与 LangChain 的比较

`@assistant-ui/react-langchain` 将子代理作为发现机制公开；AG-UI 则将其作为结构公开。`useLangChainSubagents()` 返回一个以命名空间为键的映射，并将消息获取留给调用方（参见[子代理和子图视图](/docs/runtimes/langchain#subagent-and-subgraph-views)）；而此运行时会直接嵌套消息，不提供发现钩子。两种运行时都不提供对方的结构，这种差异源于协议而非偏好：AG-UI 在生命周期事件上携带明确的 `parentToolCallId`，提供了 LangChain 的命名空间方案无法实现的精确关联，因此这里可以进行嵌套，而那里不行。

## 支持的事件

运行时会解析 AG-UI 事件流，并将每种事件类型映射到 assistant-ui 状态。

| 事件 | 作用 |
| --- | --- |
| `RUN_STARTED` / `RUN_FINISHED` | 切换线程 `isRunning`。`RUN_FINISHED.outcome` 会被遵循（成功 / 中断）。 |
| `RUN_CANCELLED` | 将正在处理中的助手消息标记为已取消。 |
| `RUN_ERROR` | 将消息标记为出错；触发 `onError`。 |
| `TEXT_MESSAGE_START` / `_CONTENT` / `_END` | 将文本内容流式传输到助手消息中。 |
| `TEXT_MESSAGE_CHUNK` | 在没有显式生命周期的情况下追加增量。 |
| `THINKING_START` / `_END` | 包裹推理块（当 `showThinking` 启用时）。 |
| `THINKING_TEXT_MESSAGE_*` | 流式传输思考文本增量。 |
| `REASONING_START` / `_MESSAGE_*` / `_END` | 按消息流式传输结构化推理。 |
| `TOOL_CALL_START` / `_ARGS` / `_END` | 将工具调用流式传输到当前助手消息中。 |
| `TOOL_CALL_CHUNK` | 在没有显式生命周期的情况下流式传输工具增量。 |
| `TOOL_CALL_RESULT` | 将工具结果附加到工具调用。 |
| `SUBAGENT_STARTED` | 为子代理运行打开嵌套助手消息，并将其附加到名为 `parentToolCallId` 的工具调用。 |
| `SUBAGENT_FINISHED` | 完成嵌套消息并记录 `result`；`suspended` 结果会将其标记为 `requires-action`。 |
| `SUBAGENT_ERROR` | 使用 `message` 将嵌套消息标记为出错，并将 `code` 记录为 `errorCode`。 |
| `STATE_SNAPSHOT` | 替换代理的外部状态。 |
| `STATE_DELTA` | 将 JSON Patch 风格的增量应用到代理状态。 |
| `MESSAGES_SNAPSHOT` | 替换完整消息列表（用于恢复线程）。 |
| `CUSTOM` | 作为 `data` 部分追加到正在处理中的助手消息。 |
| `RAW` | 解析后忽略；无法识别的线路事件类型会被规范化为 `RAW`。 |

### 自定义事件

`CUSTOM` 事件是协议为应用定义数据提供的扩展机制。每个事件都会按照到达顺序，作为规范化的 `data` 部分追加到正在处理中的助手消息：`CUSTOM { name: "sources", value: {...} }` 会变为 `{ type: "data", name: "sources", data: {...} }`。重复的名称会追加为独立的部分，`value` 会原样透传，并且每次运行都会重置数据部分。携带 `parentMessageId` 的工具调用会锚定在该消息下，而不是锚定在其在线路中的位置，因此，即使某个数据部分到达得晚于工具调用，也可以在该工具调用之后渲染。如果某次运行仅通过 `MESSAGES_SNAPSHOT` 传递其助手消息，而没有流式文本或工具调用，那么当快照取代正在处理中的消息时，该运行的数据部分会被丢弃。

通过注册按名称区分的渲染器来渲染这些事件；没有注册渲染器的部分不会显示，除非注册了 `Data` 回退组件。在这种情况下，回退组件会接收每个自定义事件名称，包括下面列出的框架基础设施事件。

```tsx
import { useAssistantDataUI } from "@assistant-ui/react";

useAssistantDataUI({
  name: "sources",
  render: ({ data }) => <SourceList sources={data.sources} />,
});
```

数据部分会保留在 assistant-ui 消息中，但不会发送回代理，因为 AG-UI 助手记录没有用于存储这些数据的字段。历史记录适配器（包括 assistant-cloud 适配器）会将其作为消息 JSON 的一部分持久化。框架集成会通过此通道发送自己的基础设施事件（`on_interrupt`、`PredictState`、`Exit`、`hook_error`、`state_update_error`、`system:*`、`MultiAgentHandoff`），这些名称会像其他名称一样显示为数据部分，因此只为后端负责的名称注册渲染器。

## 功能支持

| 功能 | 支持情况 |
| --- | --- |
| 流式文本 | 是 |
| 思考 / 推理块 | 是 |
| 工具调用和结果 | 是 |
| 工具结果交接（客户端执行） | 是 |
| 子代理（嵌套 `ToolCallMessagePart.messages`） | 是，但有[两项限制](#subagents) |
| 状态快照和增量 | 是 |
| 自定义事件（作为 `data` 部分） | 是 |
| 取消 | 是 |
| 消息编辑 | 是 |
| 消息重新加载 | 是 |
| 运行恢复 | 是 |
| 中断（人在回路） | 实验性（`unstable_*` API，参见[中断](#interrupts-experimental)） |
| 多线程 | 实验性（`adapters.threadList`） |
| 历史记录持久化 | 通过[历史记录适配器](/docs/runtimes/concepts/adapters#history-adapter) |
