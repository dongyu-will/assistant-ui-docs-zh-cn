本指南假设你已经完成了[可恢复流](/docs/guides/resumable-streams)中的基本接入，重点介绍在承载生产流量之前需要补充的内容。

## 身份验证与授权

默认的恢复端点会为任何知道 `streamId` 的调用方提供服务。应将该 id 视为不透明标识符，而不是凭据。在获取时将每个新创建的 `streamId` 绑定到请求用户，并在每次恢复时验证该绑定。

将绑定与其他会话状态存储在一起，或在 Redis 中使用单独的键存储。下面的示例使用并行的 `<keyPrefix>:owner:<streamId>` 条目，其 TTL 与底层流保持一致。

```ts title="/lib/resumable-context.ts"
import { createResumableStreamContext } from "assistant-stream/resumable";
import { redis } from "@/lib/redis";
import { store } from "@/lib/resumable-store";

const OWNER_PREFIX = "aui:resumable:owner";
const OWNER_TTL_SEC = 24 * 60 * 60;

export const resumableContext = createResumableStreamContext({ store });

export async function bindStreamToUser(streamId: string, userId: string) {
  await redis.set(`${OWNER_PREFIX}:${streamId}`, userId, { EX: OWNER_TTL_SEC });
}

export async function assertStreamOwner(streamId: string, userId: string) {
  const owner = await redis.get(`${OWNER_PREFIX}:${streamId}`);
  if (owner !== userId) {
    throw new Response("Not Found", { status: 404 });
  }
}
```

使用所有权检查包装 `resume`。返回 404（而不是 403）可以避免确认调用方无权拥有的流是否存在。

```ts title="/app/api/chat/resume/[streamId]/route.ts"
import { assertStreamOwner, resumableContext } from "@/lib/resumable-context";
import { getSessionUserId } from "@/lib/auth";

export async function GET(
  req: Request,
  ctx: { params: Promise<{ streamId: string }> },
) {
  const userId = await getSessionUserId(req);
  if (!userId) return new Response("Unauthorized", { status: 401 });

  const { streamId } = await ctx.params;
  await assertStreamOwner(streamId, userId);

  const stream = await resumableContext.resume(streamId);
  if (!stream) return new Response("Not Found", { status: 404 });

  return new Response(stream, {
    headers: { "Content-Type": "text/event-stream" },
  });
}
```

## 无服务器环境中的 `waitUntil`

在 Vercel 和 Cloudflare 上，请求处理程序会在返回响应后被销毁，生产者任务也会随之终止。如果没有 `waitUntil` 钩子，持久化流会在发起请求结束的瞬间停止增长，因此重新连接时只能看到响应刷新前恰好写入的字节。

在 Vercel 上，从 `next/server` 传递 `after`：

```ts title="/lib/resumable-context.ts"
import { after } from "next/server";
import { createResumableStreamContext } from "assistant-stream/resumable";
import { store } from "@/lib/resumable-store";

export const resumableContext = createResumableStreamContext({
  store,
  waitUntil: after,
});
```

在 Cloudflare Workers 上，从处理程序中获取 `ExecutionContext`，并转发 `ctx.waitUntil`：

```ts title="/src/worker.ts"
import { createResumableStreamContext } from "assistant-stream/resumable";
import { store } from "./resumable-store";

export default {
  async fetch(req: Request, env: Env, ctx: ExecutionContext) {
    const resumableContext = createResumableStreamContext({
      store,
      waitUntil: (promise) => ctx.waitUntil(promise),
    });
    return handle(req, resumableContext);
  },
};
```

在长期运行的 Node 服务器（自定义 Express 应用或容器）中，可以省略 `waitUntil`；生产者任务与处理程序运行在同一个事件循环上，不会被抢占。

## TTL 策略

流会在最后一次写入 24 小时后过期。此默认值适合典型的聊天工作负载：用户可能在午餐后重新加载页面。但每次部署都应有意选择合适的数值。

- 当数据块包含敏感载荷（PII、草稿、内部文档）时，应缩短 TTL。5 到 30 分钟通常足以覆盖重新加载场景，同时不会长时间保留可恢复的字节。
- 对于可能合理地持续超过一天的长期运行代理任务，应延长 TTL。将 TTL 设置为高于最坏情况下的任务持续时间，以便生产者仍能完成最终处理。
- 确保各层的 TTL 一致。存储 TTL、所有者绑定 TTL，以及引用 `streamId` 的任何签名 Cookie 都应同时过期；否则其中一个会比另一个存活更久，导致数据意外泄露或返回 404。

在存储上配置全局默认值，并在上下文中配置每次部署的覆盖值：

```ts
import {
  createInMemoryResumableStreamStore,
  createResumableStreamContext,
} from "assistant-stream/resumable";

const store = createInMemoryResumableStreamStore({
  defaultTtlMs: 30 * 60 * 1000,
});

export const resumableContext = createResumableStreamContext({
  store,
  ttlMs: 30 * 60 * 1000,
});
```

Redis 适配器接受相同的 `defaultTtlMs` 选项。

## 多租户键隔离

当多个应用或租户共享一个 Redis 实例时，应按环境设置 `keyPrefix`，这样一个租户中的配置错误流就不会与另一个租户发生冲突，也不会被一并删除。该前缀会成为每个元数据键和数据键的首段。

```ts title="/lib/resumable-store.ts"
import { createClient } from "redis";
import { createRedisResumableStreamStore } from "assistant-stream/resumable/redis";

const client = createClient({ url: process.env.REDIS_URL });
await client.connect();

export const store = createRedisResumableStreamStore(client, {
  keyPrefix: `aui:${process.env.APP_NAME}:${process.env.TENANT_ID}`,
});
```

按租户设置前缀也能降低事件响应成本。借助 `SCAN MATCH aui:app:tenant-42:*`，你可以审计或清理单个租户，而不会影响其他租户。

## 可观测性钩子

`ResumableStreamContextOptions` 提供用于结构化日志记录、指标和追踪的生命周期钩子。钩子异常和被拒绝的 Promise 会通过 `console.error` 报告，但不会影响流输出或存储的生命周期状态。

```ts title="/lib/resumable-context.ts"
import { createResumableStreamContext } from "assistant-stream/resumable";
import { logger, metrics } from "@/lib/observability";
import { store } from "@/lib/resumable-store";

export const resumableContext = createResumableStreamContext({
  store,
  onAcquire: (streamId, role) => {
    metrics.increment("resumable.acquire", { role });
    logger.info("resumable.acquire", { streamId, role });
  },
  onAppend: (streamId, byteLength) => {
    metrics.histogram("resumable.append.bytes", byteLength);
  },
  onFinalize: (streamId, status, error) => {
    metrics.increment("resumable.finalize", { status });
    logger.info("resumable.finalize", { streamId, status, error });
  },
  onError: (streamId, error) => {
    const message = error instanceof Error ? error.message : String(error);
    logger.error("resumable.error", { streamId, error: message });
  },
});
```

保持同步钩子中的工作轻量。`onAcquire` 会在生产者和消费者的 `run()` 请求路径上运行，而其余钩子会在生产者的流式传输热路径上运行。返回的 Promise 会被监测其失败情况，但不会等待其完成。

## 资源限制

内存存储会强制执行三个上限，而 Redis 适配器则有意将这些限制交给底层数据库处理。当你的进程可能被不受信任的调用方访问时，应始终设置这些限制。

```ts
import { createInMemoryResumableStreamStore } from "assistant-stream/resumable";

const store = createInMemoryResumableStreamStore({
  maxChunkBytes: 64 * 1024,
  maxEntriesPerStream: 5000,
  maxStreams: 10_000,
});
```

- `maxChunkBytes` 会拒绝行为异常的生产者发起的超大写入（例如失控的工具结果，或意外通过管道传输的 base64 数据块）。生产者任务会快速失败，而不是持续占用内存。
- `maxEntriesPerStream` 会限制每个流的条目数量。这限制了单个流在开始报错前能够增长到的大小；应结合 TTL 使用，以便已完成的流快速清理。
- `maxStreams` 会限制存活流的总数。在共享开发环境和单租户容器中，这可作为保护措施；在无服务器部署中，平台已经会限制并发量。

这些限制存在于内存存储中。对于 Redis，请在服务器上配置 `maxmemory` 和驱逐策略，并依赖上游的应用层速率限制。

## 事件响应

streamId 可能通过响应标头、浏览器会话存储、服务器访问日志，以及（在某些配置中）错误报告泄露。如果怀疑其中任何渠道已遭到入侵，应将所有正在进行的 stream id 视为已暴露。

应预先记录以下信息，以便在需要时使用：

- 每次 `acquire` 调用的获取用户 id、请求 id 和 IP（通过 `onAcquire`）。
- 每个流的完成状态（以及任何错误）（通过 `onFinalize`）。
- 所有者绑定的写入和读取，以及用户 id 和 streamId。

事件期间需要轮换或使其失效的内容：

- 在存储上递增 `keyPrefix`。现有流将变得不可访问，新流则会进入轮换后的命名空间。
- 使引用任何缓存 streamId 的签名会话 Cookie 失效。
- 删除受影响用户的所有者绑定键（按用户限定作用域的 `DEL aui:resumable:owner:*`），强制恢复操作通过新的获取流程进行。
- 临时缩短 `defaultTtlMs`，以便任何孤立流快速过期。

轮换后，应在服务器端重新生成 stream id，并将客户端重定向到新的获取流程；不要信任客户端已经持有的任何 streamId。
