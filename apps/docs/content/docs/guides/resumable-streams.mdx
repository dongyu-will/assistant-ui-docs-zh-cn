`assistant-stream/resumable` 让你能够跨客户端重连继续接收流式 LLM 响应。原始请求进行期间，服务器会持续将数据写入存储；如果浏览器重新加载或连接丢失，后续请求会重放已持久化的字节以及新增字节，直到生产者完成。

它适用于 `assistant-stream` 已提供的任何编码器（AI SDK UI 消息流、数据流协议、助手传输 SSE 格式或你自己的编码器），因为持久化发生在编码后的字节层。

## 解决的问题

用户发送了一段很长的提示词，暂时离开后重新加载标签页。没有可恢复流时，LLM 调用会被浪费；有了可恢复流，客户端可以从中断处继续。相同的流程也能处理移动设备连接中断，并允许在一台设备上启动的流在另一台设备上读取，但需要通过不透明的流 ID 进行控制。

如果你的响应较短，或者不关心重新加载后的恢复，标准的 `streamText().toUIMessageStreamResponse()` 路径就足够了。

## 服务端：最小接线配置

每个进程构造一次 `ResumableStreamContext`，并在多个请求之间复用它。该上下文是路由处理器与存储后端之间的连接层。

```ts title="/lib/resumable-context.ts"
import {
  createInMemoryResumableStreamStore,
  createResumableStreamContext,
} from "assistant-stream/resumable";

const store = createInMemoryResumableStreamStore();
export const resumableContext = createResumableStreamContext({ store });
```

在聊天路由中，将响应正文包装在 `ctx.run(streamId, makeStream)` 中。针对 `streamId` 的第一个调用者会成为生产者（运行你的 `makeStream` 回调）；后续调用者和重连请求则成为消费者，重放已持久化的字节。

```ts title="/app/api/chat/route.ts"
import { streamText } from "ai";
import { RESUMABLE_STREAM_ID_HEADER } from "assistant-stream/resumable";
import { resumableContext } from "@/lib/resumable-context";

export async function POST(req: Request) {
  const { messages } = await req.json();
  const streamId = crypto.randomUUID();

  const result = streamText({ /* model, messages, tools, ... */ });
  const sourceBody = result.toUIMessageStreamResponse().body!;

  const stream = await resumableContext.run(streamId, () => sourceBody);

  return new Response(stream, {
    headers: {
      "Content-Type": "text/event-stream",
      [RESUMABLE_STREAM_ID_HEADER]: streamId,
    },
  });
}
```

单独的 GET 端点会为重连客户端重放已持久化的字节。当不存在流时，`ctx.resume(streamId)` 返回 `null`；如果你更希望返回带有代码 `"missing"` 的 `ResumableStreamError`，则使用 `ctx.requireResume(streamId)`。

```ts title="/app/api/chat/resume/[streamId]/route.ts"
import { RESUMABLE_STREAM_ID_HEADER } from "assistant-stream/resumable";
import { resumableContext } from "@/lib/resumable-context";

export async function GET(
  _req: Request,
  ctx: { params: Promise<{ streamId: string }> },
) {
  const { streamId } = await ctx.params;
  const stream = await resumableContext.resume(streamId);
  if (!stream) {
    return new Response(JSON.stringify({ error: "stream not found" }), {
      status: 404,
      headers: { "Content-Type": "application/json" },
    });
  }
  return new Response(stream, {
    headers: {
      "Content-Type": "text/event-stream",
      [RESUMABLE_STREAM_ID_HEADER]: streamId,
    },
  });
}
```

该上下文还提供另外两个动词：`ctx.status(streamId)` 返回 `"streaming" | "done" | "error" | "missing"`，而 `ctx.delete(streamId)` 会删除某条流的所有持久化状态，并终止活跃的读取者。`createResumableStreamContext` 上的其余选项（`onAcquire`、`onAppend`、`onFinalize`、`onError`）是可观测性钩子，详见[可恢复流部署](/docs/guides/resumable-stream-deployment)。

## 客户端：原生集成

`@assistant-ui/ai-sdk` 在 `AssistantChatTransport` 上提供 `resumable` 选项。它会从响应标头中捕获流 ID，将 `chat.resumeStream()` 的重连请求重定向到你的恢复路由，并在响应自然结束时清除存储的 ID。将它与 `useChatRuntime` 配合使用；只要其可恢复存储报告存在待处理的 ID（包括挂载后发现的 ID），就会触发 `chat.resumeStream()`。

```tsx title="/app/page.tsx"
"use client";

import { AssistantRuntimeProvider } from "@assistant-ui/react";
import {
  AssistantChatTransport,
  createResumableSessionStorage,
  useChatRuntime,
} from "@assistant-ui/ai-sdk";
import { useMemo } from "react";
import { Thread } from "@/components/assistant-ui/elements/thread.aui";

const storage = createResumableSessionStorage();

export default function Page() {
  const transport = useMemo(
    () =>
      new AssistantChatTransport({
        api: "/api/chat",
        resumable: {
          storage,
          resumeApi: (streamId) => `/api/chat/resume/${streamId}`,
        },
      }),
    [],
  );
  const runtime = useChatRuntime({
    transport,
    onResumeError: (error) => {
      console.error("Could not resume the previous response", error);
    },
  });

  return (
    <AssistantRuntimeProvider runtime={runtime}>
      <Thread />
    </AssistantRuntimeProvider>
  );
}
```

当客户端发现存储的流 ID，但重连尝试失败时，会运行 `onResumeError`。你可以使用它显示 toast、上报遥测数据，或将线程标记为需要重试。除非已有更新的 ID 替换了失败的 ID，否则 Assistant-ui 会在回调执行后清除该 ID。

`createResumableSessionStorage` 返回一个由 `window.sessionStorage` 支持的 `ResumableClientStorage`。传入 `{ key }`，为不同路由或聊天界面设置命名空间；`key` 也接受一个 getter，该 getter 会在每次访问时延迟读取，因此你可以根据当前线程的身份派生它（参见[多个线程](#multiple-threads)）。当 getter 返回 `undefined` 时，读取操作会报告不存在待处理流，写入操作则会被丢弃。每个 key 复用同一个存储实例，因为不同实例不会同步其内存缓存。持久化条目会在重新加载后保留，而内存中的所有权机制会阻止一个已挂载的线程附加到另一个线程的待处理流。空闲的跟随者从后端获知流 ID 后，可以在对应消息存在于本地历史记录中时调用 `storage.setStreamId(streamId, threadId)`；当该线程成为当前线程时，运行时会完成附加，无需重新挂载。内置存储每个 key 保存一个待处理流 ID；[多个线程](#multiple-threads)模式为每个线程提供独立的 key，因此可以同时恢复多个线程。自定义 `ResumableClientStorage` 可以改为根据可选的 `threadId` 参数为记录设置 key，并实现 `subscribe(listener, threadId)` 以支持挂载后的更新，也可以完全替换存储方法。如果你运行在已经包装了 `fetch` 或 `prepareReconnectToStreamRequest` 的传输层上，`resumable` 选项可以与你现有的处理器组合使用。

默认的完成检测器会扫描 SSE 正文中的 AI SDK `"type":"finish"` 标记。如果使用自定义编码器，请在 `resumable` 选项上覆盖 `isFinishEvent`。

### 多个线程

上面的代码片段将待处理流 ID 存储在一个 `sessionStorage` key 下，这对于单个聊天界面是正确的。在包含多个存活线程的线程列表运行时中（`useRemoteThreadListRuntime`，由 `useChatRuntime` 包装），无论哪个线程最后操作，都会写入并清除同一个共享 key：当响应进行期间切换线程时，响应标头会将流 ID 写入共享 key；你切换到的线程会在挂载时读取该 ID 并恢复，从而把另一个会话的流重放到当前线程中。流完成时未限定范围的清除操作也可能删除另一个线程的待处理 ID。此外，重新加载后，共享 key 下的待处理 ID 会被挂载时作为主线程的线程占用；在线程列表中，这通常是一个全新的空线程，而不是启动该流的线程。

应将 key 限定到具体线程，并在每个线程的运行时钩子内部按线程构造传输层和存储，而不是在模块级别只构造一次。通过 getter 根据线程身份派生 key，使其在每次访问时延迟读取：

```tsx title="/app/page.tsx"
"use client";

import {
  AssistantCloud,
  AssistantRuntimeProvider,
  useAui,
  useCloudThreadListAdapter,
  useRemoteThreadListRuntime,
} from "@assistant-ui/react";
import {
  AssistantChatTransport,
  createResumableSessionStorage,
  useChatRuntime,
} from "@assistant-ui/ai-sdk";
import { useMemo } from "react";
import { Thread } from "@/components/assistant-ui/elements/thread.aui";
import { ThreadList } from "@/components/assistant-ui/elements/thread-list.aui";

const cloud = new AssistantCloud({
  baseUrl: process.env.NEXT_PUBLIC_ASSISTANT_BASE_URL!,
  anonymous: true,
});

function ResumableThreadRuntime() {
  const aui = useAui();
  const transport = useMemo(
    () =>
      new AssistantChatTransport({
        api: "/api/chat",
        resumable: {
          storage: createResumableSessionStorage({
            key: () => {
              const item = aui.threadListItem.getState();
              return `aui-resumable-stream-id:${item.remoteId ?? item.id}`;
            },
          }),
          resumeApi: (streamId) => `/api/chat/resume/${streamId}`,
        },
      }),
    [aui],
  );
  return useChatRuntime({ transport });
}

export default function Page() {
  const adapter = useCloudThreadListAdapter({ cloud });
  const runtime = useRemoteThreadListRuntime({
    adapter,
    runtimeHook: ResumableThreadRuntime,
  });

  return (
    <AssistantRuntimeProvider runtime={runtime}>
      <ThreadList />
      <Thread />
    </AssistantRuntimeProvider>
  );
}
```

`useCloudThreadListAdapter` 是 `useChatRuntime({ cloud })` 内部构建的同一个适配器，因此云端线程历史和附件仍可正常工作；如果要使用自己的后端，则改为传入自定义的 `RemoteThreadListAdapter`。每个线程的运行时钩子都会构造自己的传输层和存储，并以该线程的身份作为 key，因此一个会话的流 ID 永远不会被另一个会话读取或清除。当嵌套为 `runtimeHook` 时，`useChatRuntime` 是一个无操作的线程列表，因此它只会针对每个线程的传输层运行每个线程的聊天运行时；真正的线程列表是外层的 `useRemoteThreadListRuntime`。

使用 `remoteId ?? id` 并在其前加上可识别的前缀作为 key，且采用延迟读取。全新线程尚不存在 `remoteId`，但传输层会在请求发出前初始化线程，因此响应标头传递流 ID 时，getter 已会解析为 `remoteId`。重新加载后，相同会话会以该 `remoteId` 作为 ID 恢复，因此可以再次找到存储的条目并恢复待处理流。本地 ID 回退机制覆盖了从未发送过消息的线程，其 key 不会被其他对象读取或写入。仅使用本地 ID 作为 key 会破坏当前会话中创建的线程在重新加载后的恢复，因为重新加载列表时，它们的本地 `__LOCALID_` ID 会被 `remoteId` 替换。

## 存储选项

核心包提供 `createInMemoryResumableStreamStore`，用于开发和测试。状态存储在进程本地的 `Map` 中，因此服务器重启后不会保留。常用选项包括 `defaultTtlMs`、`maxChunkBytes`、`maxEntriesPerStream`、`maxStreams` 和 `gcIntervalMs`，用于定期清理。

在生产环境中，可以通过 `assistant-stream/resumable/redis`（node-redis v5）或 `assistant-stream/resumable/ioredis` 子路径使用可选的 Redis 适配器。两个适配器都会将每次追加的 `XADD` 和 TTL 刷新批量合并到一次管道往返中，以二进制形式存储分块值，并接受相同的 `keyPrefix`、`defaultTtlMs`、`pollIntervalMs` 和 `maxChunkBytes` 选项。由于每条流的 key 共享一个 `{streamId}` 哈希标签，因此集群路由可以正常工作。最终化通过服务端脚本执行，因此端点必须允许 `EVAL`；如果兼容 Redis 的服务禁用了脚本功能，则需要改用自定义的 `ResumableStreamStore`。

```ts title="/lib/resumable-context.ts"
import {
  createResumableStreamContext,
  type ResumableStreamStore,
} from "assistant-stream/resumable";

async function createStore(): Promise<ResumableStreamStore> {
  if (!process.env.REDIS_URL) {
    const { createInMemoryResumableStreamStore } = await import(
      "assistant-stream/resumable"
    );
    return createInMemoryResumableStreamStore();
  }
  const { createClient } = await import("redis");
  const { createRedisResumableStreamStore } = await import(
    "assistant-stream/resumable/redis"
  );
  const client = createClient({ url: process.env.REDIS_URL });
  await client.connect();
  return createRedisResumableStreamStore(client);
}

export const resumableContext = createResumableStreamContext({
  store: await createStore(),
});
```

对于 Postgres、Cloudflare Durable Objects、Upstash REST 或其他任何后端，可以直接实现 `ResumableStreamStore` 接口。有关接口契约的详细说明和完整示例，请参阅[自定义可恢复流存储](/docs/guides/resumable-stream-stores)。

## 生产环境检查清单

- **身份验证。** 上述代码片段中的恢复路由会向任何知道流 ID 的调用者提供服务。在获取流时，将 `streamId` 绑定到请求用户，并在恢复处理器中验证该绑定。应将 ID 视为不透明标识，而不是凭据；它可能通过响应标头、`sessionStorage`、浏览器历史记录和访问日志泄露。
- **无服务器环境中的 `waitUntil`。** 在 Vercel 和 Cloudflare 上，响应返回后请求处理器会被终止，从而中断生产者任务。构造上下文时，从 `next/server`（或平台提供的 `ctx.waitUntil`）传入 `after`，使任务能够在响应返回后继续运行：`createResumableStreamContext({ store, waitUntil: after })`。
- **TTL。** 默认情况下，流会在最后一次写入后的 24 小时过期。可以在存储上通过 `defaultTtlMs` 配置，或通过上下文上的 `ttlMs` 按部署覆盖。存储、所有者绑定 key，以及引用 `streamId` 的签名 Cookie 应使用匹配的 TTL。
- **流 ID 格式。** Redis 适配器会根据 `/^[A-Za-z0-9_.:-]{1,256}$/` 验证 `streamId`，以确保 key 格式正确。UUIDv4 即可。

有关授权、多租户 key 前缀、可观测性钩子、资源限制和事故响应的完整说明，请参阅[可恢复流部署](/docs/guides/resumable-stream-deployment)。

`assistant-stream/resumable` 导出了一个新的 `ResumableStreamError` 类，并提供代码 `"missing" | "exists" | "finalized" | "invalid-id"`；可以在恢复路由中捕获它，以区分“流已消失”和其他失败。

## `AssistantStreamController` 回调的辅助函数

如果你通过 `createAssistantStream` 而不是 AI SDK 生成流，包中提供了两个辅助函数，用于将控制器回调风格以及任意编码器连接到存储：

```ts
import {
  createResumableAssistantStreamResponse,
  createResumeAssistantStreamResponse,
} from "assistant-stream/resumable";
import { resumableContext } from "@/lib/resumable-context";

// POST handler
return createResumableAssistantStreamResponse({
  context: resumableContext,
  streamId,
  callback: (controller) => {
    /* same shape as createAssistantStreamResponse */
  },
});

// GET resume handler
return createResumeAssistantStreamResponse({
  context: resumableContext,
  streamId,
});
```

两个辅助函数默认使用数据流编码器；传入 `encoder: () => new AssistantTransportEncoder()`（或任意自定义编码器）即可覆盖。它们会自动设置 `x-resumable-stream-id` 响应标头，这正是 `AssistantChatTransport` 的 `resumable` 适配器查找的内容。
